## 第十五批：X2 设备故障闭环（台账 B-12 → C-33 / C-34，commit `4c4ec28`）

### 改造前的真实形态
报设备故障只是往 `andon_call` 插一行。设备台账还是 `running`（大屏显示"在运行"）、
工单还是 `in_progress`（排产以为还在生产）、停机多久无处可查（OEE 可用率永远算不出来）、
恢复后交期纹丝不动（停 2 小时，计划完工一秒没顺延）。**安灯沦为一块只会闪的屏。**

### 三处根因（形态各不相同，值得记住）

| 缺陷形态 | 表现 | 为什么难发现 |
|---|---|---|
| **无载体** | 停机没有表，`status` 只能表示"此刻故障"，不知道从何时起、停多久 | 不是 bug 而是缺失，日志里毫无痕迹 |
| **实现有了、入口没接** | 安灯 API 直插表，不调任何 service | 本项目已踩多次，故专门写接线测试 |
| **schema 挡住了实现** | `UpdateEquipmentRequest` 压根没有 `status` 字段 | `update_equipment` 是通用 SET，**传了就能改** —— grep service 层永远找不到，是 pydantic 在校验层挡掉的 |

### 落地
- `equipment_downtimes` 表 + `EquipmentDowntimeRepository`（`find_open` / `open_record` /
  `close_record` / `close_by_call` / `update_record` / `list`）+ `GET /downtimes`、
  `PUT /downtimes/{id}`（停机靠人工上报，填错必须能改，否则 OEE 一直错）
- 安灯联动收到 `AndonService`：报障 → 设备 `fault` + 开停机记录 + 工单 `pause`；
  解决 → 关记录算时长 + 设备 `running` + 工单 `resume` + **重排产**
- `CreateEquipmentRequest` / `UpdateEquipmentRequest` 补 `status`，`create_equipment`
  补 `status` 列，迁移 `20261031_equipment_status.py` 回填 NULL → `idle`

### 设计取舍（下次别推翻）
- **重复报障复用未关闭的停机记录**：不复用会开出两条并行停机，时长算两遍
- **时长先取整再落库、再用于重排**：两处用不同的数会出现"记录说 0 分钟、工单却顺延 0.1 秒"
- **时长 0 不改交期**：秒级抖动平白把交期往后推同样是错
- **`status` 回填取 `idle` 而非 `running`**：闲置是可解释的中间态，猜 `running` 会让可用率虚高
- **联动三步全容错**：失败只回 `data.linked.error`，不回滚安灯本身 —— 报障是既成事实

### 探测脚本（`e2e/equipment_fault_loop_e2e.py`，18 段）
首跑 7 通 / 6 断。**三处口径收紧**，否则会假通过：
1. **前置不成立要显式挡住**：A4 断时"A8 恢复"是假的（设备压根没进 fault），
   改打 `[GAP] 前置不成立` 而不是 `report`
2. **时间按 datetime 比不能比字符串**：`'...09:29:04'` vs `'...09:29:04.101083+00:00'`
   字符串序能过，换格式就翻车
3. **脚本自身秒级完成 → 时长恒 0**："重排产"这段等于没测到。补 `PUT /downtimes/{id}`
   把 `started_at` 前移 90 分钟，再断言 **顺延量 == 记录的停机时长**
