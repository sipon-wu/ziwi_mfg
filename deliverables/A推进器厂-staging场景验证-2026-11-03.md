## 4. 发现的平台缺陷（都可复现，均已修复并部署到 staging 复验）

### 4.1 B-4 · 改单接口无法补挂工艺路线，且空 payload 直接 500

- **现象**
  - `PUT /api/v1/work-orders/{id}` 带 `{"route_id": 168}` → **HTTP 500**，`sqlalchemy.exc.OperationalError: near "WHERE": syntax error`，SQL 是 `UPDATE work_orders SET  WHERE tenant_id = ? AND id = ?`。
  - 带 `{"route_id":…, "assigned_org_id":…}` 时会返回 **200，但 route_id 仍是 NULL** —— 比 500 更危险的那类"接口成功、结论是空的"。
- **根因**：`app/schemas/production.py::UpdateWorkOrderRequest` **缺 `route_id` 字段**（`CreateWorkOrderRequest` 有）。Pydantic 把未知字段丢掉 → `model_dump(exclude_unset=True)` 为空 → `_build_set_clause({})` 拼出 `SET  WHERE`。
- **影响**：工单建错路线、或建单时路线还没发布（传了 NULL）→ **路线永久为空，没有任何补救入口**；工序报工、流转卡、齐套都与路线脱钩。
- **修复**（已上线）
  1. `UpdateWorkOrderRequest` 补 `route_id`；
  2. `ProductionService.update_work_order` 对空 payload 抛 `400-0003「没有需要更新的字段」`，不再 500。
- **验证**：本地 `scripts/verify_local_backend_fixes.py` → 3/3 PASS；**staging 复验 `PUT route_id=168` → 200，回读 168（B-4 PASS）**。

> ⚠️ 修复只解决"以后能改"，**9 张存量工单的 `route_id` 仍为空**（建单时路线还没发布的 UN1/UN2/UN3/RT3 等）。补齐它们需要用 `PUT` 逐张回填，属数据修复，未在本轮自动执行。

### 4.2 V8 · 安灯"添加响应记录"接口必 500

- **现象**：`POST /api/v1/andon/calls/{id}/responses` 4/4 全 500，`andon_response` 一行都写不进去；但状态流转（acknowledged → resolved）正常。
- **根因**：`app/repositories/andon_repo.py::create_response` 的 INSERT 要求绑定参数 `:response_time_seconds`，而 API 层从未提供该字段（`CreateAndonResponseRequest` 只有 action/comment）。
- **影响**：安灯"从呼叫到响应"的时限统计整条链路是空的；现场追溯"谁多久接的单"答不出来。
- **修复**（已上线）：API 层按「呼叫创建时间 → 本次响应」计算秒数写入。
  - ⚠️ 修复中又踩一个时区坑：SQLite 的 `func.now()` 是 **naive UTC**，直接和 `datetime.now()`（本地 CST）相减会整整 +28800s（8 小时）。naive 一律按 UTC 解释。
- **验证**：本地 200、可回读、`response_time_seconds=0`，3/3 PASS；**staging 补建 4 条响应全部回读成功**。

> **数据要单独补**：接口修好了不等于历史数据会自己长出来。4 张呼叫是故障期间造的、响应记录 0 条，而验证脚本 V8 只读不写 → 会永远红。为此新增 `scripts/backfill_andon_responses.py`（幂等，默认 dry-run，`--apply` 才写），补建 4/4 成功，V8 转 PASS。
>
> **口径核对**：补建后 `response_time_seconds≈27536`（7.6h），看着像"少算 8 小时"，实测无误 —— 容器时区是 UTC，`call_no` 用 `datetime.now()` 取的是容器时钟（UTC 17:40 = 本地次日 01:40），`created_at` 与之自洽，7.6h 正是真实间隔。
> **遗留观察（MINOR）**：单号时间戳是 **UTC 口径**，比业务本地时间早 8 小时，跨零点会差一天（`ANDON-20261102174000` 实为本地 11-03 01:40）。同类问题值得全站排查一遍单号生成口径。

### 4.4 附带发现：`POST /work-reports` 无幂等键

重放一次报工就再累加一次 `completed_qty`（无 `request_id`、无"同工单同工序同日期"去重）。这与台账里已登记的 **R2（`issue-order-items/{id}/issue` 无服务端幂等键）** 是同一类风险：前端锁只防同页双击，网络重试/断网重发会重复计产。

### 4.5 E-E3-6b · 红冲把货还错行：同批号多行时按"批号文字"匹配会落到幽灵行

**这是本轮 E2E 抓到的第 3 个真实服务端缺陷，也是最隐蔽的一个** —— 接口 200、`reversed_qty=5`、库存总数完全对得上，但货还错了行。

现场（本地库实测，物料 59 / 仓库 5 / 库位 28）：

| 库存行 | `batch_id` | `batch_no` | 红冲前 | 红冲后 | 判定 |
|---|---|---|---|---|---|
| `id=92` | 70 | `B-1031195744` | 26 | **21** | 原批次行**没回位**，少 5 |
| `id=122` | **NULL** | `B-1031195744` | 241 | **246** | 幽灵行**多收** 5 |

根因是两层：

1. `_create_issue_tx` 写流水时 **`batch_id` 写死 `None`**，只留 `batch_no` 文本 —— 出库扣的是哪一行，流水里根本没记；
2. 红冲的 `_resolve_rollback_row` 只能按批号文字匹配，而候选池按"可用量降序"排，幽灵行余额更大（246 > 21）→ 命中幽灵行。

后果比"功能不生效"更糟：**功能"生效"了，只是加错了地方，所以没有任何报错**。原批次少的货永远回不来，凭空多出一坨无批次的库存，批次追溯链从此断开 —— 对一个主打追溯的场景是致命的。

修复（`backend/app/services/wms_service.py`）：

- `_create_issue_tx(..., batch_id=)` 记录**库存行自己的 `batch_id`**（自动拣选 / 物料级回退 / 显式指定三条路径全部传）；
- `_resolve_rollback_row(..., batch_id=)` 改为 **`(库位, batch_id)` 精确命中 → `(库位, 批号)` → 库位** 三级；历史流水没记 `batch_id` 时，同批号多行里**优先已登记批次行**，幽灵行排后面；
- `_build_cancel_tx_dict(..., batch_id=)` 让冲销流水也带上 `batch_id`；
- 红冲 `stock_in` 兜底路径补传 `batch_id`（否则 `find_one(batch_id=None)` 会拼 `batch_id IS NULL`，又命中幽灵行 —— 同一陷阱第四次）。

验证：

- 新增 2 个单测（`app/tests/test_issue_cancel_rollback.py`）：`test_rollback_ignores_ghost_row_with_same_batch_no`、`test_rollback_prefers_registered_batch_row_for_legacy_leg` → **6/6 PASS**；
- 后端全量单测 **1330 passed / 0 failed**；
- `wms_receipt_count_e2e.py` 复跑：**E-E3-6b ★逐行回到原值 · 全部回位**，脚本 **40 通 / 0 断**。

> 顺带修了探针自身的缺陷：`inv_state()` 原来只读 `/wms/inventory` 第一页（100 行），而该物料有 **152 行** —— "逐行比对"在截断窗口上做，会忽红忽绿。已改为翻页取全量（`paged()`）。
>
> **遗留数据**：幽灵行（`batch_id IS NULL` 但 `batch_no` 非空）是旧缺陷攒下的脏数据，本次只保证"不再往错行加"，**未做数据修复**。上 staging 前建议跑一次体检：`SELECT id, material_id, warehouse_id, batch_no, quantity FROM inventory WHERE batch_id IS NULL AND batch_no IS NOT NULL AND quantity > 0`，命中行需要人工并账。

### 4.6 拣选排序缺同秒 tie-break（FIFO/LIFO 结果不确定）

`find_available_batches` 只按 `b.created_at` 排序，而这列是**秒级精度** —— 同一秒收的两批货时间戳完全相同，先后由数据库返回顺序决定。拣选正是"扣哪一批"的决策点，顺序不确定意味着**同一批数据两次拣选可能扣不同批次**。

实测：E2E 的 LIFO 用例随机红（`lifo pick D first` / `lifo pick C remains` 两条 MAJOR，重跑又变绿）。

修复：`ORDER BY b.created_at {dir}, b.id {dir}`（FIFO 取小 id 先入、LIFO 取大 id 后入）。修复后连跑 3 次均 0 bug。

### 4.7 已登记未修：入库单接受不存在的 `warehouse_id`

`POST /wms/receipt-orders` 传一个**不存在的** `warehouse_id`（实测 43，`warehouses` 表里没有这一行）照样 200，随后 `receive`/`store` 过账也照样成功，库存行与流水就挂在一个"不存在的仓"上。

后果是隐性的：`/wms/reports/stock-summary?warehouse_id=43` 因 JOIN 不到仓库返回 **0 条**，盘点/报表看起来"这个仓没货"，而实际有 5 行 20 件。本次未修（涉及主数据校验与历史脏数据清理，需单独拍板），仅登记。

### 4.8 E2E 闸门自身修的三处「假红」

按 **"最危险的不是红，是假绿；其次是长期假红让人习惯性忽略红"**：

| 位置 | 假红成因 | 修法 |
|---|---|---|
| `closed_loop_test` | 仓库 id 写死 `WH_RAW=41` / `WH_FG=43`，本地库没有这两个仓；staging 上恰好存在 → 假红只在本地暴露 | 改为按**编码**（`WH-RAW`/`WH-FG`）从接口解析，缺失则创建 |
| `closed_loop_test` | 同上连带的 `/wms/reports/stock-summary` 返回 0 条 | 随仓库解析一并转绿（实测 25 条） |
| `wms_receipt_count_e2e` | `inv_state()` 只读第一页 100 行，实际 152 行 | `paged()` 翻页取全量 |

这三个都是**探针假设错**，不是服务端缺陷 —— 分开登记，避免污染缺陷清单。

### 4.10 已登记未修：TPM 逾期天数少算一天（口径差异）

`app/services/tpm_service.py:124`：`days = (now - due).days` —— 用**时间戳差截断**算逾期天数，不是日期差。

- 探针发本地朴素时间（`now-10d`），服务端按 UTC 解释 → 8 小时偏移 → 实际 10 天被算成 **9 天**。staging 稳定复现 3/3，本地 SQLite 全绿（**又一个只在 PG 侧暴露的差异**）。
- 影响不止显示：`escalation` 按 `days>=7` 分档，实际 7 天若算成 6 天就会从 `critical` 掉到 `urgent` —— **升级档位在临界值处会错一档**。
- **未修的原因**：正确修法要先定"业务日期按哪个时区"。系统没有业务时区配置，容器跑 UTC；按 UTC 取日期，会把"本地录入的日期型到期日"再偏一天。这是口径决策，不擅自改语义。

### 4.11 清库与重建实录（本轮新增）

用户要求「把 staging 原始数据清空，按方案书重新模拟场景」。执行过程与踩到的坑如下。

**范围与备份**

| 项 | 实况 |
|---|---|
| 清空前 | 78 个租户 / 29 MB；其中 **76 个是 E2E 探针留下的垃圾**（`探针租户1101xxx`、`角色预置eq/qc/full1101xxx`），真实的只有 `mfg_demo`（1048 工单 / 163 用户 / 1470 流水）、`mfg_stage`、`AH-THR` |

| 清空方式 | 只 `TRUNCATE` 带 `tenant_id` 的 **117 张表**（`RESTART IDENTITY CASCADE`）；**6 张平台表保留** —— 关键是不会把 `permissions`（374 条权限码）清掉，否则全员 403 |

**四个必须记下来的坑**

1. **`pg_restore --data-only` 不推进 sequence**。为了有引导账号，我从备份单独恢复 `tenants/roles/users/user_roles/role_permissions`，恢复后表里有 163 个用户、序列还停在 1 —— 紧接着 `POST /tenants` 直接 `duplicate key value violates unique constraint "tenants_pkey"`，前端只看到「内部服务异常」。修法：遍历全部表把每个序列 `setval` 到 `MAX(id)`（本轮对齐 121 个序列）。**任何"先 TRUNCATE 再 data-only 恢复"的场景都会踩这个坑。**

2. **清空后没有任何账号，创建租户的接口本身要求登录**（鸡生蛋）。最后是用备份里的 `mfg_demo` 账号体系做引导，造完 AH 场景后 `mfg_demo` 只保留账号、业务数据为空。

3. **P4 阶段不完全幂等**。为验证 ST2 判定修复，我重跑了一次 `--from p4`，结果多出 5 张收货单、2 张 NCR。所以最终是**清库后单轮重建**得到的干净数据 —— 报告里的数字都取自这一轮（`OK 122 / ERR 0 / SKIP 0`）。

4. **「耐压时间」是单点规格，把造数自己判成了 NG**。`定子电检标准` 第 3 项 `lower=60 upper=60`（必须恰好 60 秒），而造数脚本一律按 `upper*0.8` 取值 → 48 秒 < 60 → 判不合格 → AQL `Ac=0` 拒绝判合格，报「已录入 3 条检验结果，其中不合格 1 项，超过允收数」。**看着像判定接口的缺陷，实际是造数把检验单做成了 NG**。改为取区间中点后一次过。

**一个被推翻的旧结论（B-2）**

旧造数先手工建了两张 `NCR-AH-*`，把系统自动生成的 `NC-QC-*` / `NC-WR2` 盖住了，于是上一版报告写下「平台未见 judge=REJ → 自动建 NCR 的联动端点」。清库后数据干净，两张自动单浮现出来，`defect_desc` 分别写着"判定不合格（REJ），自动发起不合格评审"和"报工报废 2 件；原因：…"。

**造数遮住被测能力，比假绿更难发现** —— 它会推着团队去开发一个已经存在的功能。断言已改为按单号前缀识别系统自动生成的那一类。

## 8. 造数过程踩的坑（供后续复用）

1. **`page_size` 上限 100**：传 500 直接 422，而 422 在"取列表"里表现为空列表 → 表现为"没找到" → 重复创建。统一走 `list_pages()`。
2. **`POST /users` 重名返回 500 而非 409**：幂等回查必须按 `username`（`code` 列是空的）。
3. **`inspection_standard` 没有 `code` 列，`inspection_item` 不幂等**：只能按 `name` 匹配 + 按 `standard_id` 回查已有项。
4. **已发布路线不接受编辑步骤**（400「仅草稿状态的路线可编辑步骤」）：重跑要以"已有步骤数"为准，不能当失败。
5. **BOM `POST` 不幂等**：重跑整份翻倍（26 → 52 行），已改为按 `(产品, 物料码)` 先查后建。
6. **`input_qty/output_qty` 是 Integer**：15 台分 2 批 = 7.5 → 422，必须按整数拆分。
7. **`issue` 请求里带 `batch_no` 会走 `find_batch_rows` 分支**，匹配不上就 `400「未找到对应库存记录」`；批次应只在**明细**上写。
8. **探针字段名以实际接口为准**：`/trace/batch` 返回的是 `origin_work_orders / source_batches / affected_work_orders / output_batches`，不是 `upstream/downstream`。第一版按后者断言 → 4 项全红，是**假红**。
9. **净额不能把流水 quantity 相加**：`transfer` 是库内移动（源码位扣减不写负值，靠 `from/to` 表达），receipt + transfer 相加 = 2× 收货量。正确等式是 `库存 == Σ收货 − |Σ发料|`。第一版按"相加"断言 → 误判"库存翻倍"，也是**假红**。

> 历史偏差已消失：上一版报告里报工是 396 条（三轮重跑累计重复），清库后干净一轮是 **61 条**（覆盖 7 张工单）。**报工是本套造数里唯一"加性累积"的对象** —— 重跑一次多一批，`completed_qty` 也跟着涨，V6 恒成立但数字失真。要复现干净数字只有两条路：清库重建，或给报工做"按 (工单, 工序) 先查后建"的幂等（P4 阶段目前不是幂等的，见 §4.11 坑 3）。
