# 知微 ziwi 全场景穷举清单（v1 · 2026-10-29）

> 目的：用穷举场景的方式，把功能细节与边界条件暴露出来，作为 Beta 打磨的输入。
> 编号规则：`模块前缀-类型+序号`。类型：**S** 主流程 / **E** 异常 / **B** 边界 / **X** 跨模块联动。
> 现状标记：✅ 已通（本轮/上轮已验证）｜⚠️ 部分（功能在但流程未闭环）｜❌ 缺失｜❓ 待验证

## A. 平台底座（租户 / 组织 / 角色 / 字典 / 审批 / 流水）

| A-S1 | 开通租户 → 初始化管理员 → 首登改密 | 建 tenants / users / roles，写审计 | ✅ 三环已补齐（`tenant_onboarding_e2e` 15/0）：开通租户 → **初始化管理员**（新增 `POST /tenants/{tenant_id}/init-admin`：建账号 + 绑**本租户** admin 角色 + 置首登改密标志）→ 管理员可用初始密码登录、**登录响应回传 must_change_password** → **未改密时写操作被 403 拦、读操作放行** → 改密成功 → **改密后无需重登即可写**（标志放库里不放 JWT）→ 新密码可登录、标志已清。★**此前这两环根本不存在**：`POST /tenants` 只往 tenants 插一行、**不建任何账号**（租户『开好了但没人能进去』）；全库**没有任何首登改密机制**（无标志位、无拦截）。**★唯一未闭环：写审计** —— 116 张表里没有任何审计/操作日志类表，审计无处可写；建通用审计表属基础设施，**记台账待拍板、本轮不顺手建**（刻意保留为 GAP 而非假装已通） |

| A-E1 | 删除有下级的组织节点 | 应拒绝，提示挂载对象 | ✅ 全通（C-74，`perm_base_edge_e2e` A-E1 段 4/0）：**早已实现，本轮实测确认**（清单未更新）。删组织前查子节点数，有则 409「该组织下还有 N 个子组织，请先删除或移走子组织」，且**不级联删**（被拒后父组织仍在）；子节点清掉后正常删除。拒绝而非级联的理由：组织被误删会让 `user_organizations` 与数据范围静默失真，宁可让操作者先把人挪走 |
| A-E2 | 删除仍被用户引用的角色 | 应拒绝或转交 | ✅ 全通（C-74，`perm_base_edge_e2e` A-E2 段 3/0）：**早已实现，本轮实测确认**（清单未更新）。`RoleService.delete` 先查 `count_users`，有成员即 409「该角色下还有 N 名成员，请先把成员移出再删除」；移出后可删。为什么不连 `user_roles` 一起清：那等于**悄悄摘掉一批人的权限** —— 不报错、不提示，事后才发现某个人什么都看不到了 |
| A-E3 | 权限变更后已登录用户是否即时生效 | 需 token 刷新或前端重取 | ✅ 全通（C-74，`perm_base_edge_e2e` A-E3 段 4/0）：**即时生效，无需刷新 token / 重新登录**。根因是 `permission_guard` 每请求现查（`role_repo.get_user_permissions`），权限不进 JWT 载荷。实测：同一 token 下清空角色权限 → 下一次调用立刻 403；加回权限 → 立刻恢复 200。这是刻意设计（把权限烤进 token 会让「撤销权限」必须等过期，安全上不可接受） |
| A-E4 | 停用用户但其名下有在办单据 | 禁止停用或强制转交 | ✅ 全通（C-74，`perm_base_edge_e2e` A-E4 段 8/0）：**本轮唯一真缺口**。改造前 `PUT /users/{id}` 把 `status` 改成 `inactive` 一律 200「更新成功」，哪怕名下还有 3 张在制工单 —— 停用后这些单子变成「挂着人名的僵尸单」：谁也看不到、谁也接不了，直到有人翻库才发现。现在 inactive / disabled / locked 三种停用态都先扫五类在办单据（工单 released·in_progress·paused、待判检验单、待审审批节点、待做/在做保养任务、未关闭 NCR），有则 409 并逐类点名「工单 1 张」；被拒时状态不动。确需立即停用传 `force=true`：照停但回带 `forced_open_documents` 清单并写 `user.force_disable` 审计留痕（事后追「谁在什么情况下把人停了」只有这一处证据）。无在办单据的用户停用不受影响 |
| A-B1 | 用户无任何角色登录 | 只进首页，菜单空 | ✅ 全通（C-74，`perm_base_edge_e2e` A-B1 段 3/0）：**早已符合预期，本轮实测确认**。无角色用户登录 200（不是登录就炸）、`/auth/me` 正常返回（菜单据此渲染成空）、业务接口 403 且回带 `required` 权限码（不是 500、也不是默默放行）。缺权限时给的是可执行信息：知道该找谁要哪个权限 |
| A-B2 | 角色权限为空 | 同 A-B1 | ✅ 全通（C-74，`perm_base_edge_e2e` A-B2 段 3/0）：**早已符合预期，本轮实测确认**。空权限角色的成员：可登录、`GET /roles/{id}/permissions` 确为空、越权访问 403 并指明 `required`（实测 `M01:work_order:read`）。与 A-B1 同一条代码路径，差别只在「没角色」还是「有角色但没权限」，两者都不该 500 |
| A-B3 | 跨租户访问他人数据 | 必须 403/404，不可泄露存在性 | ✅ tenant_id 注入 |

## B. 主数据（产品 / 物料 / BOM / 工艺路线 / 工作中心 / 工序）

| 编号 | 场景 | 关键校验点 / 数据变动 | 现状 |

| B-S1 | 新建产品 → 建 BOM → 建工艺路线 → 启用 | 三者关联完整才可启用 | ✅ |
| B-S2 | BOM 多层级展开（父件→子件→原材料） | 递归展开、累计用量 | ✅ |
| B-S3 | 工艺路线版本升级 | 旧版本在制工单沿用旧版 | ✅ 修复（C-71）：工单新增 `route_id` 冻结工艺（升级是新建一行版本、不改老行，工单拿着老行 id 天然沿用旧版）。**★探针撞出两个从第一步就断的既有缺陷**：(a) `POST /routes` **100% 500** —— `create_route` 固定列缺 `status`/`created_by` 绑定参数；(b) `PUT /routes/{id}/steps` **步骤一条都存不进去** —— `batch_create_steps` 缺 `tenant_id` 等绑定参数（前端看着像保存成功，实际全空）。所谓「版本升级复制步骤」一直是在复制 0 条 |
| B-S4 | 工作中心产能设定（日产能/工时） | 排产引用 | ✅ |
| B-S5 | 工序标准工时维护 | 排产/报工偏差分析 | ✅ |
| B-S6 | 物料替代料设置 | 缺料时可替代 | ✅ 全通（新建 `e2e/material_substitute_e2e` **23/0**）：新增 `material_substitutes` 表 + `MaterialSubstituteRepository` + `SubstituteService` + `/wms/material-substitutes` CRUD，齐套检查的缺料行挂 `substitute`（plans / covered_qty / remaining_qty / substitutable）。此前**全库无替代料表、无替代逻辑**：齐套检查算出缺料就是缺料，仓库里躺着能顶替的料系统一概不知，计划员只能翻物料表人肉找，或直接走「强制下发」——而强制下发只留下「我强制了」的痕迹，**没有替代依据**。**★最关键的一条是「多个主料争用同一替代料时不重复扣」**：S 只有 350，A 吃掉 300 后 C 只能分到 50（若各算各的，C 会显示「150 < 350 够」——典型假绿）；实现上用的是**全局可用量池**逐笔扣减，不是逐行独立算。**★ratio 换算**：ratio=2 时缺口 300 只需 150 个替代料，且池余量随之从 50 涨到 200、C 从「不能完全覆盖」变「完全覆盖」——证明池是动态的。**★替代只是建议、不改 `check_status`**（缺料仍是 `failed`，替代需人工确认），避免「系统自己说不用管了」。**★自身缺料的料不能当替代料**（否则算出来是拿空气顶空气）。自替代 / 重复配置均 400。`test_material_substitute.py` 17 例。**★探针方法论修正**：第一版把期望值写死成 300/50/100，跑出 6 处 GAP，根因是造数漂移（旧后端进程下 A 的实际缺口是 200）而非功能坏；现改为**先读回 S 的真实可用量、再由实测缺口动态推导期望**，并额外断言核心不等式 `covered_C < 缺口_C`，使「争用真的发生」这一点不会被数字巧合掩盖 |

| B-E1 | 删除被 BOM 引用的物料 | 应拒绝 | ✅ 修复（C-71）：BOM 按 `material_code` 字符串引用物料，此前删除无任何引用检查 → BOM 行成孤儿（齐套按编码对不上、成本卷积断链）。现按生效 BOM 行数拒绝并给出数量 |
| B-E2 | 删除被工艺引用的工序 | 应拒绝 | ✅ 早已通（`count_references` 守卫），本轮回归确认。★此前探针假绿：步骤根本没存进库（见 B-S3），引用的前提就没成立 |
| B-E3 | BOM 循环引用（A 含 B，B 含 A） | 应检测并拒绝 | ✅ 修复（C-71）：BOM 行 `material_code` 若指向另一产品即构成隐含的产品→产品引用，A↔B 会让成本卷积/MRP 展开死循环且不报错。现 DFS 沿「material_code → products.code → 该产品 BOM 行」检测，自引用/直接环/间接环全拒并给出链路（`PB → PA → PB`）；原料（非产品）链条自然终止，不误判 |
| B-E4 | 工艺路线工序顺序/工位冲突 | 应告警 | ✅ 修复（C-71）：保存前整单校验 —— `step_seq` 重复**拒**（顺序锚点重了等于「先做哪道」没答案）、`operation_id` 不存在**拒**（幽灵工序）、同一工序重复出现**告警不拒**（清洗/检验合法重复）。整单先校验后写入，不落半截数据 |
| B-E5 | 产品无 BOM 直接下工单 | 应拦截 | ✅ 口径确认（C-71）：**不拦**是既定决策（C-44 —— 没配 BOM 不等于缺料，拦死会让新租户什么都下不下去），但建单返回 `warnings` 明示「无生效 BOM，下达时齐套检查将返回 no_bom」，下达时 `material_check_status=no_bom` 显式给出（不是假 passed）。清单「应拦截」预期**证伪**：正确做法是「不假绿 + 明示」，不是拦死 |
| B-E6 | 产品无工艺直接下工单 | 应拦截 | ✅ 修复（C-71）：工单此前与工艺路线**完全脱钩**（工单表没有 route_id，`product_routes` 映射也没被任何代码消费）。现补齐：传 `route_id` 校验存在性（幽灵 400）、非 published 告警；不传则告警「报工无法按工序归集」。同 B-E5，拦死会让新租户寸步难行，改为明示缺口 |
| B-B1 | BOM 变更时在制工单的物料需求 | 按快照 or 实时，需明确口径 | ✅ 口径确定（C-71）= **下达时快照冻结**，且在制工单后续齐套检查也按快照算（车间按下达时配方备料，中途换 BOM 等于做到一半换考题）。**★修前快照内容是错的**：`snapshot_bom` 查的是「全租户、所有产品、各自最高版本」的 BOM 大杂烩（连 product_code 都没用上，还有一条 `product_id=0` 死调用）→ 快照里混着别人家产品的料。现只快照本工单产品生效 BOM；快照为空（下达时还没配 BOM）回落实时口径 |
| B-B2 | 生效日期重叠的 BOM 版本 | 应拒绝或取最新 | ✅ 修复（C-71）取最新：`MAX(version)` 子查询必须同样受 `effective_from` 约束 —— 否则「未来生效的新版本」会把当前生效版本顶掉（v1 昨天生效、v2 明年生效 → 子查询取到 2、外层又把 v2 滤掉 → 生效 BOM 查空、齐套报 no_bom、快照变空）。现口径 =「该日期已生效的版本里取最新」，到生效日自动切换 |
| B-B3 | 单位换算（件/kg/m）不一致 | 应校验 | ✅ 告警（C-71）：平台**没有单位换算表**，物料按 kg 管、BOM 按 g 配时 `qty_per_unit` 量纲就是错的（齐套需求差 1000 倍）。建/改 BOM 时比对物料基本单位，不一致返回 `warnings` 明示量纲风险；不拦（部分行业确实按 BOM 单位领料） |

| G-E4 | 试产检验不合格 → NCR | 与量产 NCR 隔离 | ✅ 全通（C-73，`trial_edge_e2e` G-E4 段 10/0）：改造前试产检验只靠 `order_type='trial'` 字符串标，检验单与试产单**没有任何硬链** —— 判不合格自动开的 NCR 挂不回试产项目（评审会问「哪个试产的失败」答不出来），也筛不出「这批试产一共出了几张不合格单」。现在 `inspection_order.trial_order_id` 硬链（迁移 + 模型 + schema + INSERT 列），试产检验强制要求（缺则 400）、禁止混挂正式工单（混挂会把试产不合格算进量产口径）；NCR 单号 `NC-TR-<试产单号>` 一眼可分、`source_type='trial'`、描述点名试产单号并注明「不计入量产不良率」；对照验证量产 FQC 判 REJ 的 NCR 仍是 `NC-QC-` 前缀不受影响 |
| G-B1 | 试产跨部门协作（工艺+品质+生产） | 多方签核 | ✅ 全通（C-73，`trial_edge_e2e` G-B1 段 8/0）：改造前转量产只看 `reviews[0]`（最新一条）的结论 —— 三方各提交一份评审，只要**任意一条**批了就能转，「多方签核」形同虚设，等于最宽松的那一方说了算。现在同一 `review_stage` 多次提交只认最新一条，**每一方都必须签过且通过**：pending 报「以下评审方尚未签核：quality、production」，adjust/terminated 报「评审未通过(quality=adjust)」，缺谁点谁；转产成功返回 `signoff` 证据（stage + reviewer + conclusion），回答得了「这版配方是谁放行的」 |
| G-B2 | 转量产时工艺参数继承范围 | 需明确继承清单 | ✅ 全通（C-73，`trial_edge_e2e` G-B2 段 6/0）：改造前 `_write_formal_route` 只拷 7 个字段，把 `route_steps` 上决定产能与节拍的 **5 个参数全丢了** —— `setup_time_override` / `unit_time_override` / `is_parallel_eligible` / `next_step_seq` / `parallel_group`。症状极隐蔽：正式路线建出来了、工序一道不少，准备时间与单件工时却回到 0，排产算出的产能凭空翻倍，谁也不会想到是「转量产时丢的」。试产的全部意义就是把这些参数试准，丢了等于白试。现在全部继承，且转产结果**显式给出 `inherited_fields`**；带不过去的自定义键进 `not_inherited_fields` + warnings（继承范围这事的答案必须是可核对的清单，不许静默丢弃） |
